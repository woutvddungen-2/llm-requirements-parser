Example 5 - Visitor vs. Resident Access Separation

Input:

Voor het toelaten van bezoekers zal een video-intercominstallatie worden gerealiseerd met code-scroll panelen bij de entree. De toegang tot het gebouw voor bewoners zal door middel van kaartlezers en tags worden gerealiseerd.

Available doors:
door_main: OUTSIDE <-> Entree, external=true
door_resident: Entree <-> Gemeenschappelijk, external=false

Output:

{
  "system_type": "ACCESS_CONTROL",
  "version": "1.0",
  "requirements": {
    "door_rules": [
      {
        "areas": ["Entree"],
        "connects_to_areas": ["OUTSIDE"],
        "door_id": "door_main",
        "reader_types": ["INTERCOM"],
        "description": "Video-intercominstallatie voor bezoekers bij de entree (code-scroll paneel is UI, not CODE reader)"
      },
      {
        "areas": ["Gemeenschappelijk"],
        "door_id": "door_resident",
        "reader_types": ["CARD"],
        "description": "Kaartlezers en tags voor bewonerstoegang tot gemeenschappelijke ruimten"
      }
    ],
    "controller_rules": []
  }
}

Key extraction rules demonstrated across examples:
- "code-scroll panelen" is UI interface for intercom, NOT a CODE reader type
- Intercom placement lists do NOT create separate rules per position; when one position is at main entrance that later gets card readers, MERGE into ONE rule with both reader types
- "naast de [door_name]" (next to [door_name]) in placement text takes precedence over space names mentioned in same sentence
- Do NOT infer access-control rules from generic inventory mentions (e.g., "Elektrische deuren hoofdentree") unless explicit access-control properties are configured
- NO lock_type inferred from reader types, generic component mentions, or vague terms like "elektronisch sluitsysteem"
- Do NOT create rules for intermediate spaces unless explicitly described with access-control properties
