INTERPRETATION RULES

1. Replacement / exception overrides:
   "ipv", "maar", "behalve", "niet ... maar ..." → later rule replaces earlier.

2. Scope restriction:
   "alleen", "uitsluitend" → applies ONLY to that group.

3. Inheritance:
   Inheritance is mandatory and field-specific.
   Subgroups inherit by copying the broader rule first, then applying only the explicitly stated change.
   "ook" adds properties.
   "in plaats van" replaces only the conflicting property and preserves the rest.
   
   Example:
   If all binnendeuren have kaartlezer, deurdranger and sluitplaat, and
   "De serverruimte krijgt een gezichtscanner in plaats van een kaartlezer",
   then serverruimte keeps deurdranger and sluitplaat and only reader_types changes.

   Addition / accumulation:
   When the text adds a new property for the same door or group, keep one rule and add the new field.
   Example:
   - "De toegangsdeur krijgt een kaartlezer."
   - "Diezelfde deur krijgt ook een noodknop."
   → one rule with both reader_types and emergency_button

   Merging repeated clauses:
   If the same physical door is mentioned again later, do not create a second rule.
   Merge the new explicit property into the existing rule.
   This applies across sentences, bullets, paragraphs and page breaks.

   Inheritance across sections:
   If a later clause refers to the same door/group with a generic reference ("deze deur", "deze toegang", "dezelfde deuren"), resolve it back to the previously introduced rule and add only the new field(s).
   If a later clause introduces a new named target such as nooddeur, nooduitgang, vluchtdeur, personentoegang, abonnementdeur, or entreedeur, start a fresh target unless the text explicitly says it is the same door.
   Do not merge distant numbered sections merely because they reuse a generic label such as toegangsdeur, toegangsdeuren, automatische deur, buitendeur, or entree.
   Merge across sections only when the text clearly restates the same physical door by room/boundary or by anaphora such as "dezelfde deur" or "deze deur".

   Within-subsection "toegangsdeur" anaphora:
   When a single access-control subsection first describes the main entrance door with specific language (e.g., "deur van de hoofdentrees", "entree deur", "voordeur"), and then later in the SAME subsection refers to "de toegangsdeur" or "de toegangsdeuren" without naming a new room boundary, treat "toegangsdeur" as referring back to that previously mentioned entrance door.
   Example: "Voor bezoekers... deur van de hoofdentrees" followed by "Voor toegang van bewoners... kaart-/taglezers bij de toegangsdeur" → both refer to the same main_entry door, so merge INTERCOM (from first clause) + CARD (from second clause) into one rule on main_entry.
   Do NOT apply this rule across different subsections (e.g., across section breaks, page breaks, or distinct access scenarios).

   Cross-sentence component linkage (CRITICAL):
   If one sentence lists door-scoped access-control components for a subsystem (e.g., "Voor toegangscontrole worden aangebracht: ..."),
   and the immediately following sentence names the specific target doors for that same subsystem (e.g., "De toegangsdeuren krijgen..."),
   THEN carry forward the components from the list into the target-door rule.

   Key restriction: Only apply this linkage to the SPECIFIC doors named in the target sentence.
   Do NOT apply it to all available doors or all doors of a type.
   Do NOT apply it to doors mentioned in different, unrelated subsections.

   Example (CORRECT):
   - "Voor toegangscontrole worden aangebracht: kaartlezers, elektrische sloten, deurcontrole eenheden, proximity passen."
   - "De TOEGANGSDEUREN (the external entrance doors) krijgen een kaartlezer en een nooddrukknop."
   -> Only the externe toegangsdeuren (entrance doors) get:
      - reader_types: [CARD]
      - lock_type: SOLENOID_LOCK
      - door_sensor: true
      - emergency_button: STANDALONE

   Counter-example (WRONG):
   - "Voor toegangscontrole worden aangebracht: kaartlezers, elektrische sloten."
   - "De deuren van alle binnenruimten krijgen een kaartlezer."
   -> Only use the explicitly named components (kaartlezer).
   -> Do NOT add elektrische sloten to every interior door just because the first sentence mentioned them for "toegangscontrole".
   -> Apply linkage only if the target sentence is about the same subsystem (e.g., "De toegangsdeuren" = "toegangscontrole entrance doors").

   Door-scoped components to carry forward: kaartlezers, elektrische sloten, deurcontrole eenheden, deurcontact, deurstandmelder, noodknop, intercom, etc.
   Do not carry forward generic infrastructure: leidingaanleg, bekabeling, installatiedozen, etc.
   If the same current target door is later described with "elektrische deurdranger", "deurdranger", "elleboogschakelaar", or "van binnenuit", add those explicit properties to that same door rule. "elektrische deurdranger" → door_closer = ELECTRIC. "elleboogschakelaar" for leaving through that same door → exit_device = ELBOW_ACTUATED.
   Carry-forward is target-specific, not block-wide. If a later sentence names one concrete target door/group (for example personentoegang, parkeergaragedeur, serverruimte, of hoofdentree), its explicit lock/sensor/button properties apply only to that target and must not be copied onto other earlier targets from the same block.

   CRITICAL - "toegangsdeuren" references ONLY external doors:
   "De toegangsdeuren" (without naming specific rooms) refers ONLY to the external doors (is_external: true) connecting to OUTSIDE.
   Do NOT apply this to interior doors like "deur naar Technische ruimte", "deur naar Woning", or other internal space doors.
   When "toegangsdeuren" is mentioned without rooms, resolve it to external access doors and apply component linkage ONLY to those doors.

   When the later sentence says "toegangsdeur" / "toegangsdeuren" without naming rooms, prefer the resolved exterior access doors connected to OUTSIDE or the explicitly named person/visitor entrance doors.
   Within one local subsection or numbered block, keep the current resolved target doors active until the text explicitly introduces a new target. Later local sentences about deurstandmelders, noodknoppen, sloten, kaartlezers, intercom, or controller wiring apply to those same active target doors unless a new door/group is named.
   A new paragraph or bullet that explicitly names a different target door or boundary resets the active target. Do not carry components like handzender, intercom, tag, kaartlezer, slot, or noodmelder from the previous paragraph into the new target.
   If a paragraph describes a subsystem such as speedgate, slagboom, tourniquet, of in/uitrit and no matching physical door or gate exists in the available_doors list, do not project that subsystem's readers, remotes, or hardware onto a different listed door in the next paragraph.
   A sentence "bij de personentoegang" or "bij de entree" belongs to the exterior access door of that entrance. A later sentence about the scheiding / toegang to zone Y or zone Z is a different target and belongs to the boundary door between those sections.
   If a target door in the current subsection is already resolved to a `door_id`, later wording from the opposite side of that same doorway must update that same `door_id` rule. Do not emit a second mirror rule with only `areas` + `connects_to_areas`.

4. Door logic:
There are two broad groups:
   - buitendeuren
   - binnendeuren

   hints:
   - voordeur, achterdeur, buitendeur, nooduitgang, uitgang, vluchtdeur are typically buitendeuren unless stated otherwise.
   - doors of indoor spaces such as serverruimte, directiekantoor, magazijn, kantoor and vergaderruimte are typically binnendeuren unless stated otherwise.
   - toegangsdeur, toegangsdeuren, personentoegang, personeelsingang, bezoekerstoegang and entree usually refer to access from OUTSIDE into the building or controlled zone, unless the text names a different specific boundary.
   - if the floorplan shows only a small set of exterior access doors from OUTSIDE, and the text says toegangsdeur/toegangsdeuren without naming internal rooms, prefer those exterior access doors instead of all binnendeuren.

   Area-to-door interpretation:
   When an area or room is assigned door hardware, reader, lock, closer, exit or emergency properties, interpret this as applying to the doors of that area.

   Examples:
   - "De serverruimte krijgt een gezichtscanner" -> the doors of the serverruimte get a gezichtscanner
   - "Directiekantoren krijgen ook een pincodelezer" -> the doors of directiekantoren also get a pincodelezer
   - Intercom instructions belong to the physical access door they describe. "bij de personen toegang" attaches to that access door. "in het gesloten gedeelte direct achter de toegang" and "naast de abonnementdeur in de scheiding tussen open en gesloten gedeelte" both attach to the same boundary door between those sections — create exactly one rule for that boundary door_id and do not split into separate rules for each side.
   - CRITICAL - Intercom placement lists without explicit door targets: When a specification lists multiple intercom positions (e.g., "intercom in entree, in closed section, in open section") AS A PLACEMENT GUIDE, do NOT automatically create separate rules for each position. Instead:
     * The "entree/entry" intercom should be MERGED with any other components (card readers, locks, sensors) mentioned for the main entrance door.
     * Interior placement references (e.g., "in het gesloten gedeelte direct achter de toegang", "naast de abonnementdeur in de scheiding") belong to the boundary door EXPLICITLY NAMED in the placement description, not inferred doors.
     * CRITICAL PRECEDENCE for "naast X" (next to X): When placement says "naast de [door_name]", ALWAYS resolve to that explicitly named door_name, NOT to the space mentioned before it.
     * Example: "Intercom in het open gedeelte naast de abonnementdeur" → "naast de abonnementdeur" takes precedence: resolve to abonnementdeur (subscription/barrier door = door_04). Create one rule for door_04 with INTERCOM. Do NOT create a separate rule for door_03 just because "open gedeelte" was mentioned first.
     * CRITICAL: When text describes an intercom "in [space_name] naast de [door_name]", the rule belongs to [door_name], NOT to any door of [space_name]. Do not create rules for intermediate doors like "space_name to previous_space" just because the space was mentioned.
     * Only emit separate intercom-only rules when the text explicitly states a distinct access-control rule for an intermediate boundary (e.g., "intercom voor toegang tot het gesloten gedeelte" as a separate security requirement, WITHOUT SPATIAL PREFIX like "in het open gedeelte").
   - If both an entrance intercom and a boundary-door intercom are described with explicit different door targets, keep them as different door targets.
   - If an entrance door already has card-reader / lock / sensor fields and the text also gives an intercom at that same entrance, merge INTERCOM into that same entrance-door rule.
   - If a numbered block first gives an intercom "bij de personentoegang" and later in that same block says the personentoegang has card readers and a closing/alarm mechanism, keep one personentoegang rule with INTERCOM + CARD + the explicit lock/sensor fields.
   - Earlier intercom-only positions from the same numbered block stay intercom-only unless those same positions receive their own explicit lock, sensor, reader, or button wording.
   - CRITICAL - Main entrance intercom + card reader grouping: When the same access-control section mentions intercom "in de entreeruimte bij de personen toegang" (at the person entrance) and separately mentions "De personentoegang dient...voorzien van kaartlezers" (card readers at person entrance), these MUST be merged into ONE rule for the main entrance door (e.g., door_01) with both reader_types: [CARD, INTERCOM]. Do NOT split them into separate rules.
   - When intercom is listed in a component-placement section (e.g., "Intercom dient op volgende posities...") and the first position is the main entrance/entry room ("entreeruimte bij de personen toegang"), and a later requirement sentence says the entrance gets card readers, merge them into the entrance door rule.
   - If the same boundary door is described from both sides, keep one DoorRule for that door_id. Choose the protected / destination side as `areas` when one side is clearly the secured side.
   - If several sentences describe the same door, merge them into one rule. Use fields from the most specific / most detailed subsection.
   - Distinct numbered sections or headings stay independent unless the text explicitly links them to the same door.
   - An automatic-door section and an access-control section do not merge just because both mention generic toegangsdeuren. Merge them only if the text makes the same physical door explicit.
   - CRITICAL PRECEDENCE: When the ACCESS-CONTROL section (e.g., 65.5 Toegangscontrole) explicitly lists components and target doors, use ONLY those fields. Do NOT supplement with fields from other sections (e.g., 65.4 Inbraakdetectie). The access-control section is authoritative for its specified doors.
   - Exit-device hardware (elbow actuators, radar, motion sensors) from a distant automatic-door or accessibility section must NOT be added to access-control door rules. When the access-control section defines a door's properties, exit_device from any other section is ignored entirely — do not add it even as a supplementary field.

   Named areas such as serverruimte or directiekantoor are not broad door groups by themselves; only their doors inherit door properties.

5. Area splitting:
   If exceptions exist → split into:
   - specific subgroup
   - remaining group (e.g. "overige binnendeuren")
   When a subgroup is carved out of a broader group, always output:
   - the specific subgroup
   - the residual broader group using the canonical name "overige <groep>"

6. No overlap:
   door_rules areas must not overlap.
   Do not emit both an abstract group rule and concrete door_id rules for the same requirement.
   If available_doors let you resolve "buitendeuren", "toegangsdeuren", "automatische deuren", "nooddeuren", or similar groups to specific doors, output only the concrete door_id rules and omit the abstract duplicate group rule.

CRITICAL: Electronic vs Mechanical Access Distinction
   ONLY extract electronic access-control requirements (card readers, intercom, badge readers, keypads, mag locks, electric door openers, solenoid locks, etc.).
   MECHANICAL access (keys, cylinders, manual locks, keyways) does NOT count as electronic access control.
   Examples:
   - "De voordeur van ieder studio zal door middel van sleutels kunnen worden geopend" (access by mechanical keys) → Do NOT create door_rule.
   - "De studio's zullen worden voorzien van binnenpost" (intercom) → Create door_rule IF the intercom is for the same physical door.
   - "Kaartlezers voor bewoners bij de entree" → Create door_rule (electronic access).
   - "Sleutels voor directie, rood/wit/blauw" → Skip entirely (mechanical keys, not electronic).
   When a requirement text mentions both electronic systems (e.g., intercom at entrance) and mechanical keys (e.g., for individual unit doors), create rules ONLY for the electronic systems.
   Do NOT infer that unit doors described as "key-only" have any electronic access-control properties.
   If a specification clearly states that studio, apartment, or unit doors are accessed by mechanical keys only (sleutels, cilinder), do not create access-control rules for those unit doors.

7. Do NOT infer:
   - No lock from door closer
   - No direction from reader type
   - No reader_direction from generic kaartlezer(s), paslezer(s), badgelezer(s), or intercom. Only set reader_direction when IN, UIT, in/uitlezer, aan weerszijden, or equivalent wording is explicit. "aan weerszijden" always maps to IN_OUT. Once reader_direction is established (e.g. from "aan weerszijden"), do not remove or change it when merging additional reader types such as intercom from a later sentence.
   - Do not infer reader_direction from "aan de zijde van X", "naast de deur", "bij de inrit", "bij de entree", or similar placement wording. Those phrases locate the device physically but do not establish IN_ONLY or OUT_ONLY.
   - No explicit absence fields from silence. Do not emit `NONE`, `false`, or any other explicit "not present" value unless the text clearly states absence, such as "geen", "zonder", "niet aanwezig", or equivalent wording.
   - If the text does not explicitly state absence, omit the field instead of outputting `NONE`. This applies especially to lock_type, door_closer, reader_direction, exit_device, and emergency_button.
   - No reader_types = OTHER for generic door hardware, automatic-door hardware, or devices that map more specifically to exit_device, lock_type, emergency_button, or door_sensor
   - No emergency button from a door contact or alarm contact
   - No exit_device from emergency-door buttons: Panic buttons and alarm controls are NOT exit devices. Only set exit_device when the text explicitly names exit hardware like "drukstang" (push bar), "elleboogschakelaar" (elbow switch), or motion sensors explicitly for exiting.
   - No access-control rules from inventory mentions of doors with electronic locks: When a specification lists "Elektrische deuren hoofdentree" or "Elektrische deurkluiven" as a generic provision in a subsystem inventory, do NOT infer an access-control rule for that door unless the text EXPLICITLY describes access-control configuration (e.g., reader types, door sensors, emergency buttons) for that door.
   - Example: A provisions list containing "Elektrische deuren hoofdentree" and "Videofoon-/intercom installatie" does NOT create a rule for main_entry. Create a rule ONLY if the text later explicitly says "De hoofdentree krijgt een intercom" or "Toegang tot de hoofdentree met kaartlezer".
   - No hallucinated doors: Do NOT create rules for doors not explicitly named in the access-control section. Inventory mentions like "Toegangscontrole systeem" are subsystems, not individual door targets.
   - No secondary door inference from space names: When a requirement text explicitly names a target door (e.g., "naast de abonnementdeur", "in de scheiding tussen X en Y"), do NOT create a secondary rule for a door merely because a space name was mentioned in the same sentence. Only create one rule for the explicitly-named target door.
   - Do not create door rules from requirements in general building, electrical, plumbing, ventilation, or painting sections that are not part of the access-control specification. A deurcontacten or deurstandmelder requirement in an electrical installation section (e.g., under a heading like 'Deurcontacten', 'Kabelaanleg', or 'Installatieonderdelen') does not generate a door_sensor rule unless it is explicitly inside the access-control section.
   - No side-hint from "binnenzijde" or "buitenzijde" alone. Use exit_device_side_hint or emergency_button_side_hint only when the text explicitly relates that side to the reader side, for example "zelfde zijde als de lezer" or "tegenoverliggende zijde van de lezer".
   - No side-hint from "parkeergaragezijde", "gebouwzijde", "gangzijde", or any other plain area-side wording alone. Those phrases identify a location, not a reader-relative side hint.
   - No side-hint from physical placement wording like "naast de deur", "bij de deur", or "naast de kaartlezer" unless the sentence explicitly states SAME side / opposite side relative to the reader.
   - Even if both a reader and an emergency device are described on the same named area-side (for example both on the parkeergaragezijde), do not emit SAME_AS_READER unless the text explicitly compares the two devices.
   - Unnamed "sluit-mechanisme" stays generic (map as OTHER), and "alarmeringsmechanisme" only becomes a door sensor when the text is about a door contact / magnetic contact
   - Do not map GfS EN Exit controlsysteem / GfS TA alarmsysteem to exit_device unless the text explicitly says exit knop, elleboog, uitrijlus, or bewegingssensor
   - "Deuropenerinstallatie" (door opener installation) is a CONTROL DEVICE, not a lock type. Do NOT infer lock_type from this term. Deuropenerinstallatie refers to the electronic controller/actuator, not the lock mechanism — omit lock_type entirely unless a specific lock type (magneetslot, elektrisch slot, etc.) is explicitly named.
   - Do not duplicate the same intercom instruction as separate rules when it refers to the same physical door
   - Do not create a new rule for a door just because a later line adds a lock, sensor, reader, intercom, or emergency function
   - Do not drop door_sensor from "sluit- en alarmeringsmechanisme" when that wording is used for a concrete person access or access-control door
   - Code-scroll panelen / codepanelen are UI interface components for intercom systems, NOT CODE reader enums. Do not extract "CODE" reader type from "video-intercom met code-scroll panelen" — only extract INTERCOM.
   - No lock_type inference from reader types. Example: paslezers (card readers) or kaartlezers do NOT imply SOLENOID_LOCK, MOTORIZED_LOCK, or any lock type unless explicitly stated in text (e.g., "elektrisch slot", "magnetisch slot").
   - Generic "sluitsysteem" / "elektronisch sluitsysteem" wording is not specific enough for a lock enum by itself. Do not output lock_type from this phrase alone unless the text also names a concrete lock mechanism such as elektrisch slot, magneetslot, sluitplaat, motorslot, or solenoidslot.
   - "elektronisch sluitsysteem" by itself does not justify lock_type = OTHER either. If no concrete lock mechanism is named, omit lock_type entirely.
   - A generic access phrase like "voorzien van een elektronisch sluitsysteem" must never be the sole reason to output lock_type = OTHER. If the mechanism is unspecified, omit lock_type.
   - Even when the same sentence also mentions tag, pas, kaartlezer, elleboogschakelaar, or groene melder, "elektronisch sluitsysteem" still does not justify any lock_type unless the lock mechanism itself is explicitly named.
   - A concrete lock type named for door/group X must not be copied onto a different door/group Y that only has generic "sluitsysteem" wording.
   - If a rule would otherwise contain only door_id/areas plus an inferred generic lock_type = OTHER from vague "sluitsysteem" wording, omit that rule entirely.
   - Generic component mentions like "Deuropenerinstallatie" that are not explicitly tied to a specific door should NOT generate lock_type inferences. Only set lock_type when a door lock (not opener/controller) is explicitly assigned to a named door (e.g., "De serverruimte krijgt een magneetslot").
   - Generic inventory or installation list lines like "videofoon-/intercom installatie", "elektrische deuren hoofdentree", or "toegangscontrole parkeergarage" do not by themselves create a DoorRule. Only later concrete door-scoped requirement sentences may do that.
   - When requirement distinguishes between visitor access (e.g., "bezoekers intercom") and resident/employee access (e.g., "bewoners kaartlezers"), create separate rules targeting different door_ids. Do not merge them into a single rule.
   - If individual woning / appartement / studio doors are explicitly described as key-only (sleutels, cilinder, gewone deurkruk) and no supported access-control hardware is assigned to those unit doors, do not emit access-control rules for those unit doors. Keep the building access hardware on the shared entrance / circulation door that controls entry for residents or visitors.

8. High-value term mappings:
   Keep these mappings short and literal. Do not expand them into broader guesses.
   - kaartlezer / kaartlezers / kaartlezer(s) / IN kaartlezer / in kaartlezer → reader_types includes CARD, reader_direction = IN_ONLY when "IN" is explicit
   - kaartlezers aan weerszijden / aan weerszijden voorzien van kaartlezers → reader_types includes CARD and reader_direction = IN_OUT
   - pincodelezer / codelezer / keypad → reader_types includes CODE
   - intercom / spreekunit / personenintercom → reader_types includes INTERCOM when it is clearly the access device
   - deurcontact / deurcontacten / standmelder / deurstandmelder / deurcontrole eenheden → door_sensor = true
   - elektrische sloten / elektrisch slot → lock_type = SOLENOID_LOCK (when found in a component list, carry this forward to all target doors in the same subsection via cross-sentence linkage)
   - MIVA-openingsysteem / elleboogschakelaar / elleboogknop → exit_device = ELBOW_ACTUATED only when this requirement appears within the access-control section itself and explicitly describes the exit mechanism for that specific controlled door. Do not apply from a general automatic-door, building-automation, or accessibility section.
   - radar / aanwezigheidssensor / bewegingssensor → exit_device = MOTION_SENSOR when the text is about exiting through the door
   - nooddrukknop / ontgrendeldrukknop / noodknop → emergency_button = STANDALONE
   - databus / bus / RS485 → connection_type = BUS
   - sluit- en alarmeringsmechanisme → lock_type = OTHER plus door_sensor = true only when the alarm part is a door contact or magnetic contact
   - elektrische sloten / elektrisch slot → lock_type = SOLENOID_LOCK (only when explicitly stating the LOCK type, not the opener/controller)
   - deuropenerinstallatie / deuropener → NOT lock_type. This is a control/actuator device. Omit lock_type unless a specific lock type is also mentioned (e.g., "deuropenerinstallatie met magneetslot").
   - GfS EN Exit controlsysteem / GfS TA alarmsysteem → do not force into exit_device unless the sentence explicitly names one of the supported exit-device enums

11. Controller scope:
   For controller_rules, `manages_door_areas` must list only the areas of the door_rules that the same access-control subsection actually targets.
   Do not copy every floorplan area into `manages_door_areas`.

9. Ambiguous alternatives:
   When a sentence uses "of" between two device names, do not invent both unless the source text explicitly says both are included.
   If the surrounding sentence makes one mapping concrete (for example one device is clearly an access trigger and the other is only an alternative wording), choose the concrete mapping and keep the rest of the rule unchanged.

10. Replacement
   Replacement is field-specific, not whole-rule replacement: "in plaats van" replaces only the conflicting field, all other inherited fields remain.

DESCRIPTION RULE
- Must summarize ONLY structured fields.
- No extra interpretation.
- No ignored information.

GOAL
Produce final, non-overlapping rules. Do not output intermediate reasoning.
When available_doors are provided, always expand to one rule per physical door — do not group multiple doors into a single rule.

DOOR RESOLUTION

is_external flag:
- The `is_external` flag on each door is authoritative. Do not override it based on space names.
- `is_external: false` → binnendeur, always. Even if the space is named "Entree", "Lobby", or similar.
- `is_external: true` → buitendeur, always.
- When a requirement targets "alle binnendeuren", include every door with `is_external: false`.

door_id:
- When available_doors are provided, resolve each rule to a specific door and set `door_id`.
- Each rule targets exactly one door. When multiple doors match, emit one rule per door with the same fields.
- Do not omit `door_id` when the mapping is known.
- If no door in the list matches the requirement, still emit the rule using `areas` and `connects_to_areas` — do NOT suppress the rule. The door list may be incomplete.

areas with door_id:
- `areas` must always be set, even when `door_id` is set.
- Use the space name(s) from the requirement text that identify the door — not both sides from the door map.
- Example: "serverruimte krijgt een paslezer" → areas=["serverruimte"], even if the door also connects to "hal".

connects_to_areas:
- When `door_id` is known AND the door is external (connects to OUTSIDE), ALWAYS set connects_to_areas = ["OUTSIDE"].
- When `door_id` is known AND the door is internal (both sides are named spaces), NEVER set connects_to_areas.
- When `door_id` cannot be resolved, set connects_to_areas only if the text explicitly says "van X naar Y" (naming both spaces).
- For external doors: door_id identifies the door uniquely, but connects_to_areas = ["OUTSIDE"] must still be included to show it is an external boundary.

Direction mapping for "van X naar Y":
- X is the source/unsafe side → put X in `connects_to_areas`
- Y is the protected/destination side → put Y in `areas`
- Example: "deur van Hal naar Serverruimte" → areas=["Serverruimte"], connects_to_areas=["Hal"]
- NEVER put the same space in both `areas` and `connects_to_areas`.
